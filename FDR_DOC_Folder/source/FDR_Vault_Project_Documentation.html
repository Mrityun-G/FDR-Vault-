1Project at a Glance

FDR Vault is a working prototype of the AICTE Intelligent Regulatory Validation Platform (AI-IRVP). It digitises how AICTE approves technical institutions and manages each institution's security deposit, kept as a Fixed Deposit Receipt (FDR) under joint lien with the Regional Officer, AICTE.

Institutions apply and manage their deposits from a mobile app (installable web app and Android APK). AICTE scrutiny officers, bank officials and administrators work in a staff website with two portals. Both front ends talk only to the project's own API server, and one PostgreSQL database enforces every rule, permission and status change. Documents are read automatically and checked against AICTE norms before a human looks at them, the issuing bank confirms the lien, and the system reminds institutions before every maturity.

2Problem Statement

Under AICTE's approval process, an institution keeps a security deposit / corpus fund as a Fixed Deposit Receipt for a 10-year term, under irrevocable joint lien in favour of the Regional Officer, AICTE. The issuing bank marks the lien in its Core Banking System (CBS). The deposit must be renewed before it matures, and the lien can be discharged only after AICTE approves its release. Each approval application (new programme, extension of approval, intake change and others) is also scrutinised against norms for documents, faculty, built-up area and the deposit.

When this is handled with paper receipts, letters and spreadsheets, the following problems appear:

ChallengeImpact
FDR receipts and bank letters checked by handSlow scrutiny, inconsistent decisions, typing errors in deposit numbers, amounts and dates.
Lien confirmed by letter or emailNo reliable record of which bank official confirmed the lien, when, and with what CBS reference.
Maturity dates tracked manuallyDeposits lapse without renewal; releases are approved late or without checking maturity and lien status.
Same document reused by different institutionsRecycled or forged evidence is hard to notice when files are checked one application at a time.
Requirements spread across handbook clausesInstitutions submit incomplete requests, which leads to repeated deficiency notices and delays.
No single register of depositsHard to report corpus held, deposits awaiting verification, upcoming maturities and pending requests.
No tamper-evident record of decisionsWeak accountability: changes to records and decisions cannot be proven later.
Goal: one secure, centralised platform where every deposit and application is captured once, checked automatically against the norms, confirmed by the bank, monitored until maturity and released through a recorded, auditable decision.

3Proposed Solution and Innovation

Objectives

  • Give institutions a mobile-first, bilingual app to apply, upload documents, submit FDRs and track every request.
  • Validate automatically against AICTE norms on the server, so officers start from findings instead of raw paper.
  • Put the issuing bank in the loop: only that bank's official can confirm the joint lien and record its discharge.
  • Monitor every deposit until maturity with automatic reminders, and control renewal, replacement and release.
  • Keep a tamper-evident audit trail and strict separation between institutions, banks and AICTE roles.

What makes FDR Vault different

1 · Rule-checked before human review

Seven norm checks (documents, certificate validity, identity, duplicates, faculty ratio, built-up area, FDR corpus) produce Passed / Warning / Critical findings with handbook clause labels.

2 · Cross-institution fraud detection

The SHA-256 fingerprint of every uploaded file is compared on the server against all institutions' filings, which no single institution could see.

3 · Evidence-based document reading

Values are read from the FDR advice with the page and line they came from and cross-checked against the form (GREEN / AMBER / RED). A free path (PDF text rules + Tesseract OCR) works without any AI key.

4 · Bank in the loop

Bank officials see only their own bank's deposits. They confirm the lien with a CBS reference and later record its discharge.

5 · Complete FDR lifecycle

New FDR → lien confirmation → reminders at 180 / 60 / 30 days and at maturity → renewal or replacement → release order → bank discharge.

6 · AI assistant that never invents rules

The Regulatory Assistant shows the source and verification status of every required document. Only verified or portal rules can block a submission.

7 · Tamper-evident audit

The audit log is append-only and hash-chained per institution (prev_hash → sha256_hash), so any edit breaks the chain.

8 · Mobile-first and inclusive

Installable app and Android APK, full English / हिन्दी interface, offline banner, built for low bandwidth and small screens (320 px and up).

5System Architecture

FDR Vault is a three-tier system. Two front ends are static sites on Vercel. One Node.js API server on Render holds every secret and is the only component that connects to PostgreSQL. Browsers never connect to the database.

Architecture principles

  • The database decides permissions. Each API request runs in its own transaction as the PostgreSQL role authenticated with the caller's user id set, so the schema's grants and row-level security policies apply to every read and write.
  • The server is authoritative. Clients never write tables. Every change goes through a SECURITY DEFINER function that checks identity, role, institution and the allowed status transition, then writes an audit event.
  • Only granted functions are callable. The RPC gateway reads the list of functions granted to signed-in users from the database catalog (never a hard-coded list) and passes all values as query parameters.
  • Two run modes for the institution app. Server mode (when config.js has API_URL) uses the real backend. Demo mode (empty API_URL) runs the same screens and rules on the device, so the app can be evaluated offline.

10Deterministic Rule Engine

Rules run on the server inside PostgreSQL (function _evaluate) when an application is validated (dry run) or submitted. Each finding records its rule code, clause label, severity (PASSED WARNING CRITICAL), description, rule version and whether it is deterministic. If server validation is unavailable, the app blocks submission; a failed check is never treated as a pass.

FDR field validation function _check_fdr

  • FDR / TDR number: letters, digits, / and -, at least 6 characters, and unique across the whole portal.
  • Bank and branch required; IFSC must match AAAA0XXXXXX (11 characters, e.g. SBIN0001234); amount greater than zero.

11Document Upload, Reading and Validation

Upload and storage

  • Accepted formats: PDF, JPG, PNG, up to 10 MB per file. Each category can be uploaded once per application.
  • The file's SHA-256 fingerprint and page count are computed on the device; the server re-checks the fingerprint format and that the file really exists in storage.
  • Files are stored privately in PostgreSQL under <institution_id>/…. Upload and read are allowed only in the institution's own folder; there is no update or delete, so evidence is immutable. Files are opened through short-lived signed links.

Reading ladder free first, AI optional

#ReaderHow it works
1PDF text + fixed rulespdf.js takes the PDF's own text; fixed rules find the FDR number, amount, issue and maturity dates, bank, depositor and lien holder, keeping the page and line of each value. Deterministic, no AI, no cost.
2OCR (Tesseract)For photos and scanned PDFs (page images stored as JPEG). Bundled English data, nothing downloaded at run time; about 1–2 s per page, one document at a time. Confidence below 70% counts as partly legible (AMBER). Can be switched off with OCR_ENABLED=false.
3Claude (optional)Only when ANTHROPIC_API_KEY is set on the server: model claude-opus-5-5 reads the document and flags anomalies. A refusal or truncated answer is treated as an error, never as a silent pass. The result is advisory; the statutory rules still run in PostgreSQL.

Cross-checks against the form

The reader compares what it found with what the institution typed: institution name (similarity ≥ 60%), FDR number, deposit amount, issue and maturity dates, bank (similarity ≥ 50%), lien holder (must be AICTE), validity date, faculty counts by cadre, issuing authority and reference number. The outcome is shown as:

GREEN checks passed   AMBER partly legible or needs manual review   RED mismatch or wrong document (for example, a different document placed in the FDR-advice slot)

Where reading happens. The application wizard and the AI Regulatory Assistant read documents. The plain "Submit New FDR" form records the deposit without reading the file. In the wizard, submission is never blocked by reading; in the Assistant, a RED document must be corrected and re-uploaded before submission.

12FDR Lifecycle Management

A deposit moves through the states below. Renewal, replacement and release are requests (PENDING → APPROVED / REJECTED): the deposit changes only after an AICTE administrator approves (decide_fdr_request) and, for a new or replacement deposit, after the bank endorses the lien (bank_endorse_lien).

Bank confirmation of the joint lien

The bank official enters the CBS endorsement reference (at least 6 characters). The FDR then records who confirmed it, shown on every screen:

Confirmation sourceMeaning
BANK_OFFICIALConfirmed on the portal by an official of the FDR's own bank (the strongest evidence).
AICTE_RECORDEDEntered by an AICTE administrator from a bank token; the institution is told the bank has not confirmed it on the portal.
DEMO_SIMULATEDSeeded demo record.
UNRECORDED / PENDINGOlder record without an endorsement on file / not yet confirmed.

Maturity reminders

  • Job run_daily_reminders runs at most once per India date, from 07:00 IST, under a database lock so only one server runs it, and logs each run (trigger, FDRs checked, notifications created, error) in job_runs.
  • Every API server calls it at start-up and every 10 minutes, so a restart or a sleeping free instance catches up. A GitHub Action wakes the server at 07:05 IST and again at 08:35 IST.
  • For every active FDR with a confirmed lien: an alert at 180, 60 and 30 days before maturity and on maturity ("eligible for lien release"). Alerts within 60 days are Critical, earlier ones are Warnings. Each alert is sent once per FDR, maturity date and window.
  • New reminders appear in-app and are emailed to the institution's active accounts (written to the server log when SMTP is not configured).
  • Administrators see the job's status and the last 10 runs in Settings and can press Run now.

Decisions on requests

  • Every decision needs a reasoned note (≥ 10 characters). Renewal sets the new maturity date and adds 10 years to the tenure. Replacement records the new FDR number, bank, branch, IFSC, amount and maturity, keeps the old number, and resets the lien so the new bank must endorse it.
  • Release needs the AICTE release order number (and date). The bank official can read the release order on their own bank's FDRs and then records the lien discharge with a CBS reference; the institution is told to contact the branch for payment.

Regulatory honesty

  • Sources and requirements live in the database and are maintained by administrators in Regulatory Sources. Each source is VERIFIED, PORTAL_RULE, UNVERIFIED or OUTDATED.
  • Only Verified and Portal rule requirements can block a submission; unverified ones are shown for human confirmation. The default catalog marks the AICTE handbook as Unverified; no clause is invented.
  • Blockers: a missing mandatory document, a RED document, a missing required form field or a value that conflicts with the document. AMBER documents and unverified requirements appear as warnings for manual review.
  • Without an AI key, uploads that cannot be read are AMBER and the user types the values (nothing is guessed); free-text requests are classified by keywords. Uses the same ANTHROPIC_API_KEY as document reading.

15Security and Data Protection

Access control

  • Role checks inside every workflow function; status transitions allowed per role in SQL.
  • Row-level security: an institution reads only its own rows; a URL or id of another institution returns nothing.
  • Bank isolation: bank officials see and act only on their own bank's FDRs.
  • Staff-only review notes live in a separate table institutions cannot read.

Authentication & sessions

  • Passwords hashed with bcrypt (pgcrypto, cost 10).
  • Access tokens valid 1 hour, refreshed automatically with rotating refresh tokens (30 days); only token hashes are stored.
  • Logout or a revoked session works immediately; changing the password signs out other sessions.
  • With "Remember me" off, the session is kept only for the browser tab.

Abuse protection

  • Rate limits: sign-in 10 per 10 min per email and 30 per IP; one OTP or reset email per minute; 5 code attempts per 10 min; sign-up 10 per hour per IP; Assistant 120 calls per minute per user.
  • Email links and Google sign-in return only to the configured front ends; CORS allow-list.
  • helmet security headers; Vercel adds nosniff, X-Frame-Options DENY and a strict referrer policy.

Integrity & evidence

  • Audit log append-only and hash-chained per institution (prev_hash → sha256_hash).
  • Documents immutable (no update or delete), private, opened with short-lived signed links.
  • Cross-institution SHA-256 duplicate detection on the server.
  • Idempotent submissions; every status change saved in status history.

Secrets

  • Front ends contain no keys; the API server reads every secret from environment variables.
  • In server mode no institution records are stored on the device.

Safe AI use

  • AI and OCR output is advisory only; statutory rules decide.
  • An AI refusal or truncated output is an error, never a pass.
  • AI service down → manual review (AMBER), never a silent approval.

21Simulated Features and Current Limitations

The prototype is honest about what is real and what is simulated. Simulated features are clearly labelled in the app.

Simulated by design

  • Aadhaar e-Sign and DSC token signing, until an eSign Service Provider (ESP) is integrated.
  • Issuing-authority checks (DTE, University, Fire, NBA, bank CBS) shown in Compliance & Verification and Settings.
  • AI document summaries in demo mode, and in server mode until ANTHROPIC_API_KEY is set (the free PDF-text and OCR readers work without it).

Current limitations

AreaLimitation
Bank integrationNo live connection to bank CBS: the bank official types the CBS reference. A bank can confirm a lien; there is no "discrepancy" outcome.
AICTE systemsNo API integration with existing AICTE portals; Government SSO (SAML) is hidden on the standalone server.
Regulatory catalogThe AICTE handbook source is Unverified until an administrator records the section and excerpt.
RemindersAlerts at 180 / 60 / 30 days and on maturity; no overdue flag or escalation after maturity.
ReportsExport is CSV only; notices and letters print to PDF from the browser.
EncryptionData is protected in transit (HTTPS) and by access control; there is no application-level encryption at rest beyond the host's defaults.
RegistrationSelf-registration is open for every role so evaluators can try each portal; production should restrict staff roles to invitations.
HostingFree-tier Render instance (sleeps when idle) and free PostgreSQL plan; not sized for production traffic.
AndroidDebug APK only; Google sign-in is not available inside the Android WebView (email/password and OTP work).
